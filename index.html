EdgeMind · Adaptive Runtime SDK

Run any AI model on the device you already have, configured and improved automatically.

What it solves

Five problems that stop companies running AI on their own machines

Open AI models are free to use, but running them well on ordinary hardware, and trusting what they say, is hard. EdgeMind removes each blocker with rules, measurement and one small learning agent.

The model does not fit or runs slowly

ProblemDefault settings ignore the device: freezes, crashes, or a few words per second.
EdgeMindReads the model and free memory first, refuses unsafe setups, compresses the model, and tunes itself on that exact machine.

One compression level for every task

ProblemA small version is fast but makes more mistakes; a large one is accurate but slow. Usually one is chosen for everything.
EdgeMindAnswers on the fastest version and moves to a more accurate one only when that task needs it.

Confident but wrong answers

ProblemA model can invent a database column or a total, and the answer looks just as sure as a correct one.
EdgeMindChecks SQL, code, JSON and numbers with fixed rules; every answer is passed, retried on a stronger version, or marked failed.

Sensitive data cannot go to the cloud

ProblemCustomer, financial and health data often may not leave the company's own systems.
EdgeMindEverything runs on the device. No prompt or answer is sent anywhere.

Long conversations get slow and confused

ProblemSending the whole history every time makes prompts long and mixes topics together.
EdgeMindKeeps one memory section per task and sends only the relevant facts, inside a fixed token budget.

Nobody knows what a model can really do here

ProblemLeaderboards measure full-size models on large GPUs, not the compressed copy on your laptop.
EdgeMindMeasures each task on this device and keeps the pass and fail record per task and version.

How the SDK works

Five stages, every time a model runs

The first three stages happen once, when the model is loaded. The last two repeat with every reply, so the setup keeps improving.

STAGE 1

Inspect

Reads the model file and measures the device before anything is loaded.

Model layers, size per layer, memory per word of conversation · CPU cores, free RAM, GPU memory
STAGE 2

Plan safely

Lists every possible way to run the model and removes those that would not fit or would hurt quality.

Precision versions × CPU/GPU split × threads × batch, checked against free memory minus a safety reserve
STAGE 3

Start fast

Predicts the fastest safe setup, or quickly measures each version, and starts there.

Short speed test per precision (about 5 s); compressed versions can be created automatically
STAGE 4

Run & protect

Answers requests while watching memory, temperature and speed; recovers instantly from failures.

Live telemetry, switching before memory runs out, rollback to the last working setup
STAGE 5

Learn & improve

Scores each reply and learns which setup works best on this device; prepares the next change in the background.

Reinforcement learning (Q-learning); knowledge saved per model and per device
↻ Stages 4 and 5 repeat after every reply. Only how the model runs changes; the model's knowledge is never modified.

The research, explained for everyone

How can a bank use AI on its own cheap computers, without trusting wrong answers?

This is the question the research answers. Use the switch to read it in plain words or in precise technical terms; the facts are the same. The question behind the research: per-task selection of the cheapest execution profile that stays correct, on commodity on-premises hardware, with deterministic verification and tabular Q-learning as the only learned component.

1 · Three walls stop banks using AI today

1Privacy

Customer data often may not be sent to outside AI services. Data-residency and confidentiality requirements push inference on-premises; external inference APIs are often not permitted.

2Cost

Running AI on their own machines usually means buying expensive GPU servers. On-premises fleets are commodity CPUs with limited RAM, which forces small open models and aggressive quantization (Q4/Q8).

3Trust

AI sometimes gives wrong answers that look confident. In finance, one wrong total or account number is costly. Quantization degrades accuracy by an unknown amount per task, and there is no cheap, standard way to verify outputs or prove fitness per task.

2 · The idea in one sentence

For every type of job, find the smallest, cheapest version of the AI that is proven to do that job well enough, use it, and check every answer it gives. For each task, select the lowest-cost execution profile (base model + optional LoRA adapter + precision map) whose 95% Wilson lower bound on gold accuracy is within 5 points of the full-precision baseline (non-inferiority); route requests to it, verify every output deterministically, and escalate to the next profile on failure.

3 · Think of a bank branch with junior and senior clerks

A sensible manager tests each junior clerk on each kind of work, gives every job to the cheapest clerk proven good at it, has a checker verify each finished job, sends failures to a senior, and keeps a register for the auditors. EdgeMind does the same with versions of an AI model.

air_sdk/engines/space.py
def check(self, pos, budget, blacklist) -> Rejection | None:
    """Deterministic safety rules. Returns None if safe. O(1)."""
    if not self.in_range(pos):
        return Rejection.OUT_OF_RANGE
    if not self.precision.is_quality_ok(pos.variant, pos.kv):
        return Rejection.QUALITY
    est = self.estimate(pos)
    if est.ram_bytes > budget.ram_bytes:
        return Rejection.RAM
    if est.vram_bytes > budget.vram_bytes:
        return Rejection.VRAM
    if self.config_at(pos).key in blacklist:
        return Rejection.BLACKLISTED
    return None

The red cubes in the 3D view

Before any setup is used, it must pass these fixed rules: quality limit, free RAM, free GPU memory, and "has not failed before". The learning agent can only choose among setups that pass.

Budget = free memory now + memory the current model would release − a safety reserve.

air_sdk/rl/qtable.py
def update(self, state, action, reward, next_state, next_mask, *,
           alpha, gamma, prior=0.0, next_priors=None):
    """Q(s,a) <- Q(s,a) + alpha * (r + gamma * max Q(s',a') - Q(s,a))"""
    old = self.q(state, action, prior)
    target = reward + gamma * self.max_q(next_state, next_mask, next_priors)
    td_error = target - old
    new = old + alpha * td_error
    self.set(state, action, new, self.visits(state, action) + 1)
    return new, td_error

How it learns

Tabular Q-learning: after each reply, the value of "this action in this situation" moves toward the reward it actually produced plus the best value reachable next. No neural networks, so every number can be inspected.

Saved per model and per device, so learning survives restarts.

air_sdk/rl/reward.py
t   = clamp(m.tokens_per_second / baseline.tokens_per_second, 0, 4)
lat = clamp(baseline.ttft_s / m.ttft_s, 0, 4)
mem = clamp(1 - m.peak_memory_bytes / m.memory_budget_bytes, -1, 1)
q   = clamp(m.quality_loss / max_quality_loss, 0, 1)
switching = weights.switching * switching_share(m.switch_s, m.request_s)

total = (weights.throughput * (t - 1) + weights.latency * (lat - 1)
         + weights.memory * mem - weights.quality * q - switching)

What "better" means

Each reply is scored on speed, time to first word, memory left free and measured quality loss, minus any time the user waited for a reload. The weights change with the goal you pick.

Failures (e.g. out of memory) receive a fixed penalty and are avoided afterwards.

air_sdk/quantize.py
def quantize_q8_0(rows):
    """Q8_0: per 32 values, d = max|x| / 127 (fp16), qs = roundf(x / d) (int8)."""
    blocks = rows.reshape(-1, QK)
    amax = np.abs(blocks).max(axis=1)
    d = amax / np.float32(127.0)
    inv = np.divide(1.0, d, out=np.zeros_like(d), where=d != 0)
    out = np.empty(blocks.shape[0], dtype=_Q8_DTYPE)
    out["d"] = d.astype(np.float16)
    out["qs"] = _roundf(blocks * inv[:, None]).astype(np.int8)
    return out.tobytes()

Compression on the device

Turns a full-precision model into an 8-bit (or 4-bit) version, block by block, in the exact format llama.cpp uses. Tests check the output byte for byte against llama.cpp's reference method.

0.68 GB → 0.36 GB (8-bit) → 0.21 GB (4-bit) in about 13 s.
